# M2 acceptance

This page records the required rung contract and the evidence available for it. Local checks remain optional. Only remote CI or the adopting platform pipeline is a hard gate. Rung execution establishes no live agent enforcement; see [agent contracts](../agent-contracts.md) for that separate evidence.

## Reproduce

Run the functional catalog from a complete candidate checkout:

```sh
go run ./tools/acceptance -m2
```

Run the native measurements separately, with no competing test load:

```sh
GOLAW_M2_MEASURE=1 go test -race -timeout=45m -run '^TestM2Measurements$' -count=1 -v ./tools/acceptance/
```

These commands build versioned candidates, use isolated repositories and configuration, install and verify pinned tools, and exercise real binaries. Preparation needs the candidate's dependencies and tool releases available to its private caches. Ordinary package tests use simulated executors and do not establish real tool latency.

A transient error from the Go checksum database while installing a pinned tool fails setup-clean and every following row that consumes its tools. Run the command again: setup-clean deliberately installs into an empty cache, so an earlier installation does not avoid this dependency. A measurement attempt stopped during preparation is Unmeasured, with no samples to publish.

The native m2 CI job publishes measurements; release acceptance does not rerun them. The required m2 job times the push rung against a fixture database; live-database timings come from the scheduled or manual m2-live job. To reproduce the live lane, also set GOLAW_M2_LIVE_DB=1 for the measurement command.

The m2 matrix uses ubuntu-latest, macos-latest and windows-latest. The separate m2-live job runs on ubuntu-latest. Measurements appear in the test log and GITHUB_STEP_SUMMARY; the jobs do not create a separate downloadable measurement artifact.

## Required functional rows

The catalogs contain 46 rows: 16 staged-state rows, 21 lifecycle rows and 9 installed-rung rows. Every row is required on Linux, macOS and Windows except windows-shell-only, which is required on native Windows and an optional SKIP elsewhere. A required SKIP never counts as PASS. An expected refusal in a red fixture is a passing acceptance row only when the intended diagnostic and state assertions also hold.

The command column names the operation under assertion after fixture preparation. golaw denotes the immutable candidate binary, not go run. For installed hooks, HOOKS denotes the effective directory returned by git rev-parse --git-path hooks and checked against the setup receipt. sh denotes the resolved shell used to execute that installed file, Git's shell on Windows. MSG denotes a fixture message path containing a space; URL also contains a space in installed push rows. These are symbolic names, not machine paths.

### Staged state

All rows below are required on all three systems and run `golaw scan --staged --json`. Each preserves HEAD, checkout bytes and both indexes, including raw index bytes. A near row requires exit 0, a clean staged report and no findings; ordinary red rows require exit 1 with the named enforced finding. The policy red row requires exit 2 and its key and repair.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| partial-red | `golaw scan --staged --json` | A partially staged change introduces text.dashes; partially restored checkout lines do not hide it. |
| partial-near | `golaw scan --staged --json` | The staged content is clean while the checkout contains the dash. |
| opposite-red | `golaw scan --staged --json` | The index contains the dash while the checkout is clean. |
| opposite-near | `golaw scan --staged --json` | Reverse the two contents; only the clean index is judged. |
| deletion-red | `golaw scan --staged --json` | Deleting an old violation does not cancel a new one in new.txt. |
| deletion-near | `golaw scan --staged --json` | A staged deletion removes the violation even when the file remains in the checkout. |
| rename-red | `golaw scan --staged --json` | A rename introduces a dash in new.txt. |
| rename-near | `golaw scan --staged --json` | Moving an inherited dash does not introduce another finding. |
| dirty-red | `golaw scan --staged --json` | A staged violation in dirty.txt survives restoration of its checkout bytes. |

### Installed routing and child git

These rows invoke the installed hook files after checking their receipt and effective routing. A red row requires a nonzero refusal naming the intended cause; its near control must succeed. Pre-commit and spawn-git rows preserve HEAD, checkout bytes and index entries by path, mode, object ID and stage. Lefthook can refresh index stat data while hiding and restoring unstaged files, so these rows compare copied index listings rather than raw index bytes.

| Row | Command | Red or control relationship | Systems |
| --- | --- | --- | --- |
| installed-pre-commit-red | `sh "$HOOKS/pre-commit"` | An index dash remains enforced despite clean unstaged checkout content. | Required on all three |
| installed-pre-commit-near | `sh "$HOOKS/pre-commit"` | Clean staged content passes despite a checkout dash. | Required on all three |
| installed-commit-msg-red | `sh "$HOOKS/commit-msg" "$MSG"` | An invalid subject is refused with commit.conventional. | Required on all three |
| installed-commit-msg-near | `sh "$HOOKS/commit-msg" "$MSG"` | A conventional subject passes; the spaced message path remains one argument. | Required on all three |
| installed-pre-push-red | `sh "$HOOKS/pre-push" local "$URL"` with one ref pair | Real govulncheck reports reachable synthetic GO-2026-0001 from the fixture database. | Required on all three |
| installed-pre-push-near | `sh "$HOOKS/pre-push" local "$URL"` with one ref pair | The empty fixture database passes with commit-time tools absent from PATH. | Required on all three |
| spawn-git-red | `sh "$HOOKS/pre-commit"` with test_staged true | The staged failing test is refused despite the checkout holding the passing child-git test. | Required on all three |
| spawn-git-near | `sh "$HOOKS/pre-commit"` with test_staged true | The staged child-git test passes despite a failing checkout test and inherited linked-worktree and alternate-index variables. | Required on all three |

The push rows use a real pinned scanner with controlled local advisory data, not the live database. Their PATH omits golangci-lint and gitleaks; it retains a copy of the already verified lefthook executable for installed dispatch. Spawn-git rows append the case's original PATH after verified tools and prerequisites so a C compiler can support the race detector on Linux and Windows. See the [installed-rung catalog](../../tools/acceptance/m2_native.go).

## Measurement contract

The [measurement test](../../tools/acceptance/m2_measurement_internal_test.go) times the installed hooks over a copy of the kit and a small staged Go change. Preparation, candidate builds, tool installation and the warm priming invocation are outside the timed interval. Each rung has five cold and five warm samples, for 30 samples in a completed attempt. Record every sample's milliseconds and exit code in collection order, then the median and maximum for each of the six series.

Cache definitions use names only and never publish paths from the measuring machine. Each cold sample gets fresh GOCACHE, GOMODCACHE and GOLANGCI_LINT_CACHE directories. A warm series shares those three caches after one untimed priming invocation. Installed tools stay outside sample caches. Cold here does not clear the operating system page cache, upstream download caches, or every scanner cache; it is not a bare-machine installation measurement.

Each warm median is compared with the 10-second budget of its rung; a rung over it fails the m2 job. That value is m2WarmBudget. The budget is a required comparison, not a claim that an unexecuted rung is fast.

Publish each completed attempt with:

- Source revision, source-tree digest, candidate binary digest, OS and architecture. The source-tree digest hashes the candidate source bytes, including relevant uncommitted changes; it is not merely the Git revision.
- Actual Go and Git versions and the verified gitleaks, golangci-lint, govulncheck and lefthook versions.
- Database kind and source. The required lane uses `tools/acceptance/testdata/m2/empty-db`; the installed red row separately uses `tools/acceptance/testdata/m2/red-db`. The m2-live lane uses `https://vuln.go.dev` and records its reported database timestamp.
- Five raw cold and five raw warm samples per rung, all exit outcomes, six medians and maxima, and the three warm-budget comparisons.
- Both contention observations: direct pre-commit and installed pre-commit wait durations and exit codes, the holder PID named by each, and successful controls through both routes after releasing the lock.
- The immutable native CI run and job-summary links, and the final M2_MEASUREMENTS_COMPLETE marker from that same attempt.

Direct contention must exit 2 and name the holder; installed contention must refuse and name the same holder. The lock has a short wait. A nonzero pre-push exit can still be a measured advisory result when it identifies the advisory. Scanner failure, an unreachable database, an unmeasured check or a file over the read bound cannot become a completed timing merely because the optional rung returns success.

An unavailable measurement remains unmeasured and is never published as zero. Retain failed attempts as Unmeasured with their reasons and any partial output; never splice samples from different attempts into a completed run. Require both successful measurement execution and M2_MEASUREMENTS_COMPLETE before calling an attempt complete.

### Measured limit: a cold pre-commit on a large dependency graph

The kit's tree is small: one staged line there affects 8 packages. A service module is larger. On 2026-10-20, with a development build of revision 4569d08 and one staged comment line in a package of a service module that 107 packages depend on, pre-commit took a median of 3.65 seconds warm (3.43 to 3.91 seconds over five samples). Cold, with fresh GOCACHE, GOMODCACHE and GOLANGCI_LINT_CACHE, it took a median of 83.1 seconds (74.9 to 97.8 seconds over three samples). A smaller service module, one staged line affecting 3 packages, took 1.8 seconds warm and 13.0 seconds cold, in line with the kit's tree. Pre-push on the larger module took 7.3 seconds warm and 8.4 seconds cold, each sample refusing advisories that its Go 1.27.0 toolchain and a dependency carry. The cold cost grows with the packages a change affects, because go vet, golangci-lint and the package graph compile them once into the empty caches. Warm runs stay within seconds. The first commit after a cache is cleared, or on a new machine, pays that cold cost, a stated limit. These samples are not from the native CI jobs.
