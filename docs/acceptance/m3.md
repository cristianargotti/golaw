# M3 acceptance

This page records the required M3 acceptance rows and the limits of what they prove. Local checks remain optional. Only remote CI or the adopting platform pipeline is a hard gate. The rows below prove that the policy checks, the capabilities and the generated CI make a consumer's `make ci` fail on a violation and pass without one; they do not make any check on the developer's machine mandatory.

## Reproduce

Run the M3 catalog from a complete candidate checkout:

```sh
go run ./tools/acceptance -m3
```

The command builds the release candidate 0.3.0 from the checkout and serves it behind the local module proxy of the M2 harness, because a development build pins 0.0.0, which no proxy serves, and the rendered `golaw.mk` runs the kit's `depsage` and `vulngate` at the exact pin. It then installs the pinned tools through `golaw setup` in a repository of its own, verifies every pin and points govulncheck at the fixture vulnerability database, so no row reads a live advisory and every row judges the candidate, never a published kit. Each row runs in an isolated home over a repository of its own: the service fixture the kit embeds, rendered into a module and adopted with `golaw init --apply --capabilities`, or the template birth fixture under `tools/acceptance/testdata/m3/template/birth`. A candidate that cannot be prepared is the one row of the run, `m3-preparation/candidate`, and fails it.

The two dependency rows belong to the M1 catalog, which the acceptance job runs on the same three systems:

```sh
go run ./tools/acceptance
```

A release run, `go run ./tools/acceptance -release`, requires the M1, M2 and M3 rows together, so its runner needs make, bash, Node and, for the image job of the replay, Docker beside Go and git.

## Systems

The m3 matrix uses ubuntu-latest, macos-latest and windows-latest. The job `m3` of `.github/workflows/ci.yml` runs `go run ./tools/acceptance -m3` on each with fail-fast off and a 90 minute bound, so one system's failure never hides another's result.

The replay of the generated CI is required on ubuntu-latest and an optional SKIP elsewhere; a SKIP never counts as PASS. Every job the CI template renders runs on an ubuntu runner, so a replay on macOS or Windows would prove a pipeline nobody runs; the harness reports those rows as SKIP with the reason `required on linux, the system the generated CI runs on`.

Each policy row runs make -k ci, so the scan target reports its violation even where an earlier capability target fails for a tool the machine lacks. The clean baseline runs `make ci` without `-k` on every system, and the template rows run it again inside the replay on ubuntu-latest.

Every other row is required on all three systems.

## Required rows

The catalogs register 35 M3 rows: 15 policy rows, 6 named cases, 6 template rows, 4 capability rows and 4 adoption rows. The command column names the operation under assertion after fixture preparation; golaw denotes the candidate binary, not go run. The tables follow the [policy](../../tools/acceptance/m3_policy.go) and [violation](../../tools/acceptance/m3_violations.go) catalogs, the [cases](../../tools/acceptance/m3_cases.go), the [template](../../tools/acceptance/m3_template.go) and [replay](../../tools/acceptance/m3_replay.go) sources, the [capability](../../tools/acceptance/m3_capability.go) and [adoption](../../tools/acceptance/m3_adoption.go) catalogs and the [dependency rows](../../tools/acceptance/dependency.go).

### m3-policy

Each row adopts the rendered service under the capabilities it names, go alone unless the row says otherwise. A violation row first requires its check measured without a finding by `golaw scan --json .`, applies the smallest edit that breaks the check, then requires `make -k ci` to exit nonzero and name the check.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| baseline | `make ci`, then `git diff --exit-code` | The adopted service passes its own `make ci` and leaves every tracked file unchanged; it is the control of every violation row. |
| ci-target | `make -k ci` | Dropping `deadcode` from the prerequisites of `ci` in `golaw.mk` draws `policy.ci-target`. |
| dependabot-cooldown | `make -k ci` | Lowering `default-days` from 7 to 1 in `.github/dependabot.yml` draws `policy.dependabot-cooldown`. |
| dependency-records | `make -k ci` | A require of `example.test/unrecorded` that no decision record names draws `policy.dependency-records`. |
| deps-age-config | `make -k ci` | Lowering `-days 7` to `-days 1` in `golaw.mk` draws `policy.deps-age-config`. |
| generated-fresh | `make -k ci` | Removing the `generate-check` rule from `golaw.mk` draws `policy.generated-fresh`. |
| gitleaks-generic | `make -k ci` | An allowlist of the generated paths `^gen/` appended to `.gitleaks.toml` draws `policy.gitleaks-generic`. |
| golangci | `make -k ci` | Disabling the govet analyzer `shadow` in `.golangci.yml` draws `policy.golangci`. |
| gotoolchain-local | `make -k ci` | Removing `export GOTOOLCHAIN=local` from `golaw.mk` draws `policy.gotoolchain-local`. |
| image-digest | `make -k ci` | Under go and image, the first image of the `Dockerfile` left by tag draws `policy.image-digest`. |
| makefile | `make -k ci` | Removing the `deadcode` rule from `golaw.mk` draws `policy.makefile`. |
| openapi-assertions | `make -k ci` | Under api and go, removing `redocly.yaml` draws `policy.openapi-assertions`. |
| ruleguard | `make -k ci` | Removing `scripts/lint/rules.go` draws `policy.ruleguard`. |
| squawk-config | `make -k ci` | Under db and go, removing `.squawk.toml` draws `policy.squawk-config`. |
| profile-checks | `golaw scan --json .` | Without a profile, `policy.hook-tests` and `policy.codeowners-foreign` answer not applicable with a reason that names the profile, never a finding. |

### m3-cases

Each case adopts the service with go, copies it once per side, applies the red edit to one copy and the near edit of the same shape to the other, and scans each copy. Both sides require the check measured, because a stated limit proves neither a finding nor its absence; the red side requires an enforced finding of the check at exit 1 and the near side none.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| disabled-linter | `golaw scan --json .` | `errcheck` under `linters.disable` draws `policy.golangci`; the near edit disables `lll`, which the required set leaves out. |
| generated-file-allowlist | `golaw scan --json .` | A gitleaks allowlist of the paths `^gen/` draws `policy.gitleaks-generic`; the near edit allowlists the regex `^EXAMPLE-` instead. |
| hollowed-by-exclusion | `golaw scan --json .` | An exclusion of `errcheck` under `internal/` draws `policy.golangci`; the near edit excludes `mnd` in test files, which `golaw.yml` allows. |
| missing-include | `golaw scan --json .` | `include mk/absent.mk` of a file the tree lacks draws `policy.makefile`; the near edit is the optional `-include mk/absent.mk`. |
| modular-makefile | `golaw scan --json .` | The `deadcode` rule moved from `golaw.mk` to `mk/quality.mk` with no include draws `policy.makefile`; the near edit includes that file from the `Makefile`. |
| second-require-block | `golaw scan --json .` | A second require block of `example.test/second` without a record draws `policy.dependency-records`; the near edit adds `docs/adr/0002-second-module.md` naming the module. |

### m3-template

Each row adopts the service under one capability set, reads the run steps of the `.github/workflows/ci.yml` that init rendered for it and runs them in file order through bash with the real tools, as a runner does: `GITHUB_ENV` and `GITHUB_PATH` carry to the steps after them, and the first failed step fails the row. A rendered file without a run step fails the row.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| every | the rendered run steps through bash | Every capability at once, api, cli, db, go, hexagonal and image, so every job the template can render runs. |
| go | the rendered run steps through bash | The control: go alone renders the `ci` job, `make ci` then `git diff --exit-code`. |
| go-api | the rendered run steps through bash | api beside go adds the api job and its Node tool to the control. |
| go-db | the rendered run steps through bash | db beside go adds the db job and squawk to the control. |
| go-hexagonal | the rendered run steps through bash | hexagonal beside go adds the hexagonal job, `make lint`, to the control. |
| go-image | the rendered run steps through bash | image beside go adds the image job with hadolint, trivy and Docker to the control. |

### m3-capability

Each row adopts the service twice, with go and the capability and with go alone. It requires every check of the row measured without a finding on the tree with the capability, applies the same edit to both trees and scans each with `golaw scan --json .`.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| api | `golaw scan --json .` on both trees | A 5xx answered outside the errors package in `internal/server/raw.go` draws `goast.raw-error-response` with api; without api, that check and `policy.openapi-assertions` answer not applicable naming api. |
| db | `golaw scan --json .` on both trees | Removing `.squawk.toml` draws `policy.squawk-config` with db; without db the check answers not applicable naming db. |
| hexagonal | `golaw scan --json .` on both trees | Dropping the depguard rule `domain` draws `policy.golangci` with hexagonal; without it the check stays measured without that finding, because hexagonal shapes a rule inside the check rather than conditioning it. |
| image | `golaw scan --json .` on both trees | Leaving every image of the `Dockerfile` by tag draws `policy.image-digest` with image; without image the check answers not applicable naming image. |

### m3-adoption

Each row commits the template birth fixture, a service as a scaffolder leaves it before golaw, as the first commit of a repository of its own.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| birth-accept | `golaw init --apply --accept .golangci.yml`, then `golaw init --apply` | The strict asset replaces the birth's lint configuration and `golaw.yml` records its digest as managed; the second apply proposes it no more. |
| birth-older-go | `golaw init --apply` over `go 1.23` | init names the go floor 1.24 and writes no `golaw.mk`, whose targets need a newer go. |
| birth-preview | `golaw init`, then `git status --porcelain` | The preview names the targets the `Makefile` and `golaw.mk` both define, the imported modules `go.mod` marks indirect, the `Makefile` section of the merged `.editorconfig` and the capabilities the files suggest, and changes nothing. |
| birth-scan | `golaw init --apply --capabilities api,go,image` with three `--accept`, then `golaw scan --json .` | After the repairs init names and the proposals it prints, the scan measures every check: findings may remain, because the birth keeps defects its own template must repair, but no check is unmeasured and the exit is at most 1. |

### dependency

Both rows write a module whose require goes through a `replace`, adopt it with `golaw init --apply` and commit it, so the only verdict left to the scan is whether it can follow the replace.

| Row | Command | Red or control relationship |
| --- | --- | --- |
| dependency/internal-replace | `golaw scan --json .` | A replace to `./library` inside the repository is followed: exit 0 with `policy.dependency-records` measured; the control of the external row. |
| dependency/external-replace | `golaw scan --json .` | A replace to `../external-library` outside the repository is a stated limit: exit 2 with `policy.dependency-records` unmeasured and a reason that names the target, never a finding. |

## What the rows do not prove

No remote platform pipeline ran a kit stage, so the rows establish no remote hard gate: a profile's remote gate is whatever the adopting platform runs, as the [profile guide](../profiles.md) states.

The replay with the real tools covers six capability sets, go alone, go beside each of api, db, hexagonal and image, and every capability at once, while the structural replay of the `internal/assets` tests covers all 34 valid capability sets without running a real tool.

A template birth whose `.github/` another team owns gets no generated CI, so the template rows prove the pipeline of a repository whose `.github/` the kit owns, as the [starting states](../setup.md#starting-states-golaw-does-not-support) state.

The vulnerability steps of every M3 row read the fixture database the harness serves, so the rows prove the wiring of the `vuln` target, never the state of the live advisory database.

## Evidence

No run of the m3 job is recorded yet. When it runs, its immutable run and summary links for the three systems are added here with their output. A local run on one machine establishes neither remote CI success nor the result on the other systems, and a required row that did not run on a system is not waived there.
