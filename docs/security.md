# Security model

golaw checks repository content and supported agent operations. It is not a sandbox. An agent holding credentials can still act outside the guarded routes.

## Assurance levels

| Level              | Evidence                                                                       | Claim                                                |
| ------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Rule proof         | Production dispatch, red and near-miss fixtures, deletion and over-fire passes | The check distinguishes its intended violation       |
| Offline acceptance | The exact installed invocation receives recorded inputs                        | The adapter and launcher answer the protocol         |
| Live acceptance    | A dated record identifies agent, OS, version, binary, and target state         | The host dispatched and respected the installed hook |

The table below is the M1 scope, kept as history. Assurance levels for each agent and OS are recorded in the [agent contract matrix](agent-contracts.md). It holds one row per agent, event and operating system, each proven live, proven offline or documented only, and this page keeps no second matrix.

| Agent       | OS                    | M1 offline scope                                          | M1 live scope                       |
| ----------- | --------------------- | --------------------------------------------------------- | ----------------------------------- |
| Claude Code | Linux                 | Adapter and installed exec invocation                     | No live enforcement claim           |
| Claude Code | macOS                 | Adapter and installed exec invocation                     | Required for the released candidate |
| Claude Code | Windows               | Adapter, installed exec invocation, executable resolution | No live enforcement claim           |
| Codex CLI   | Linux, macOS, Windows | Outside M1                                                | Outside M1                          |
| Cursor      | Linux, macOS, Windows | Outside M1                                                | Outside M1                          |

These are release requirements, not a substitute for the recorded acceptance results. The historical macOS host evidence is in agent-contracts.md.

## What the guard stops

This section and the next describe the Claude Code guard. The Codex guard and the Cursor guard have their own sections below, each stating what it stops and what it cannot stop.

In an enrolled repository, supported pre events deny a typographic dash write, a prohibited secret read, a --no-verify commit, and an oversized candidate whose whole content can be reconstructed. An Edit is applied in memory before measurement. A shell command is read the way its shell hands the program its words: a redirection, wherever it stands and joined to a word or not, is no argument, and the name rules judge its file. A comment, from a hash that starts a word to the end of its line or a PowerShell block comment, is text no rule reads, so a quote or a here-document operator in it opens nothing. Inside an arithmetic expression, or a $[ ] or ${ } of a word, a << opens no here-document. A here-document the line never ends takes the rest of the command line as its body, as bash does, and is data unless a shell reads it. A $[ ] or ${ } that holds a blank, a newline, a parenthesis or another separator of commands, where the scanner ends the word, is beyond this reading.

The --no-verify commit is recognized where the command line spells it: behind assignments, the reserved words of a shell and the wrappers it names, each wrapper past its own options, in the script a shell, eval, Invoke-Expression, a here-document a shell reads or its line sources from the standard input, a substitution or the set of a cmd for /f runs, and in the command xargs, call and start run. A substitution is read where the shell expands it: inside a word, outside single quotes, and in the body of a here-document whose end word is unquoted, never in the body of one whose end word is quoted. A command line built while it runs is beyond that reading, because reading it would need a full interpreter: the value of a variable or the output of a command the line expands, the input xargs reads, the lines a for /f hands its body and a variable cmd expands. So is a here-document body another program reads as commands: a body is read as a script only when its line names a shell or sources the standard input, so a body eval runs through the output of cat, one xargs or a read loop turns into arguments and the script of another interpreter, such as python3 -, are data, to the secret names too. The blocks of a PowerShell statement after its first, such as the else block of an if, are read as one command with the words before them. A substitution inside double quotes ends where bash 4 and later, zsh and dash end it, at the parenthesis that matches it past the quotes, the here-document bodies and the case patterns inside it; bash 3.2, the /bin/bash of macOS, ends it at the first parenthesis left open, so a line written to read otherwise there is beyond this reading.

The repository that holds the file a write or read names governs it, wherever the session runs. A symbolic link changes neither: the file a name leads to through every link is placed first, then the link the name opens and every directory that holds a link it passes through, so a write through a link into an enrolled repository is judged there, and a write through a link of an enrolled repository to a file outside it, the link of the file or of a directory above it, is refused as one that repository cannot place. A write outside every enrolled repository, such as the agent's own plan files, is a positively unenrolled location. A read outside every enrolled repository is judged by the session's repository, so the person's credential stores stay behind the secret boundary of an enrolled session.

Malformed input, an unreadable target, an envelope mismatch, and an unsupported mutation shape are denials. A write is judged whole up to the read bound of 8 MiB. An input over that bound is checked as one within it, its JSON to the last byte and its envelope and tool input as their decoders check them, so malformed input and an unsupported shape stay denials at any size, and in an enrolled repository it is a denial too, except a write or a post event, whose header the hook reads from the whole input in bounded memory: a post event is judged as any other, its detection needing no byte of the event, and a write is allowed with a notice naming what was not measured once the name rules allow the path it names; a write of golaw.yml stays denied at any size. The internal deadline is shorter than the host timeout; a pre event it reaches is a denial. The installed handler uses timeout 10 and onFailure: block, requiring Claude Code 2.1.295 or newer.

Post events detect changes after execution. They cannot undo writes. Shell post failure detection also runs because a command can write before a later operation fails. Detection reads only the files git status reports changed against HEAD and the index, and, after a command that moved HEAD, the files the move changed; of those, it judges only what the commits the command created changed, and names the files a pull, a checkout, a merge or a reset brought from other commits in a notice that asks for no fix; of a merge commit the command made, it judges what the merge holds apart both from every parent and from the merge git makes of its parents by itself. A merge the command starts and leaves in progress is read the same way: a file it staged whose bytes are those of the merge git makes by itself or of the commit it merges is named in that notice, a file whose staged bytes are neither, the command's own resolution or edit, is judged, and a file git leaves unmerged waits for the event that writes its resolution. What it cannot measure, a file over the read bound, a change set over its bounds, a pre event that left no baseline, a move of HEAD git cannot compare, a file git cannot convert to compare or the deadline, is a notice the agent reads, never a block. The name rules still judge a file over the read bound, so a name the tree forbids is fed back or denied without its bytes.

## What the guard cannot stop

Background writers, manual edits, hosted tools, and MCP tools outside supported event routes can bypass the guard. Claude Code @ references bypass hooks; narrow Read deny rules cover only their listed paths.

A write over the read bound, an edit of a file over it, the changes a command makes past the bounds of detection and a move of HEAD git cannot compare are left to the pipeline with a notice the agent reads; a file a command writes and commits is judged, the first commit of its branch included, the paths between the two HEADs being asked of git, while a file a move brings from a commit the command did not create is left to the pipeline with a notice that names it. A file git status reads as clean because the index tells it not to look, or because its stat data still matches the index, is invisible to detection: a command that rewrites it is left to the pipeline without a notice, as agent-contracts.md states.

A shell command is judged by the repository of the session's working directory, because its targets cannot be known before it runs. A command sent from an unenrolled directory into an enrolled repository, such as git -C, is not judged. A script run through cmd /c is read the way cmd separates its commands, past the condition of an if, the clause of a for up to its do and an else, whose names, the items of a for set, the root of a for /r and the file of an if exist, stay judged, the command the set of a for /f runs is read as the script of a child cmd /c, call and start are read as wrappers of the command after them, and the started program splits its arguments by the Microsoft runtime rules; a program that parses its command line another way, a cmd builtin included, may read the same text differently.

Four shapes of a command line, none of which a well-meaning agent writes, are read otherwise than the shell reads them; they are stated limits, not reasons to widen the reading, and a test pins the answer the hook gives each one. A hash right after the parenthesis that closes a substitution, an arithmetic expansion or a process substitution inside a word, as in x=$(true)#, begins a comment for this reading, while the shell keeps it in the word, so the commands after it on its line pass and a quote after it opens nothing. The words after the script of sh -c or bash -c, which the shell hands the script as its positional parameters, are read as words of the script, so a comment that ends the script hides them, as in bash -c 'cat "$1" # read' sh followed by a file name. The string of env -S is split as a POSIX shell splits words, so an escape env reads its own way is read as the character it escapes: `\_`, a blank to env, joins two words into one name, and `\c`, the end of the string to env, is read as a c. A line crafted for bash 3.2, which ends a substitution inside double quotes at the first parenthesis left open, is read as bash 4 and later read it, typed at the tool's shell or fed to bash through a here-document.

## The Codex guard

Codex stops a dash write and an oversized file before it exists through apply_patch when the whole candidate can be reconstructed, a secret read through Bash tokens, and a --no-verify commit. The patch grammar is pinned to the validated Codex version. An Update chunk that applies exactly to the file on disk reconstructs the whole candidate; one that does not is judged by its added lines only, with the size deferred to the post event where the host emits one.

Codex cannot stop write_stdin into an interactive interpreter, hosted and MCP tools beyond the optional matchers, an untrusted or failed hook, or background writers.

Codex has no read event: the rule runs on Bash tokens and optional MCP read matchers. Optional MCP matchers do not establish general MCP coverage. write_stdin into an interpreter, hosted tools, unsupported specialized routes and background writers remain outside the coverage claim. The secret names are the patterns of internal/checks/paths/secret.go and the credential printers those of the shell checks under internal/checks/shell, executable data with red and near-miss fixtures; this page repeats neither list and widens neither.

Codex fails open on host failures and skips untrusted hooks silently. The host failures are a timeout, a spawn failure, exit 1, termination by a signal, invalid response JSON, exit 2 with an empty stderr, disabled hooks, untrusted hooks and an untrusted project layer; Codex has no fail-closed host setting. A denial is the schema-valid deny JSON with exit 0 and the English reason on stderr, because an answer with a field outside the schema is invalid and lets the tool run. The internal budget is 8 seconds; the installed host timeout is 10 seconds. The eight-second deadline can produce a pre denial before the ten-second timeout, but it cannot fix a process that never starts or a hook the host never dispatches.

The internal deadline, prefix rules, post feedback, optional staged scanning and doctor reduce these gaps. None of them is a gate: the deadline answers before the host timeout; the prefix rules are loaded by Codex itself, apart from the hook; post feedback arrives where the host emits a post event; golaw scan --staged is optional; doctor reports trust and the current dispatch evidence, so an inert hook is never reported as protecting. Remote CI or the platform pipeline is the only hard gate.

The generated rules cover only the unconditional forbidden prefixes the shell family supplies: the families the hook denies in every enrolled repository whatever the policy says. They do not encode policy-dependent push or pull-request restrictions. A user-scope rules file also applies outside enrolled repositories. There the hook gives a valid allow, so golaw.rules is written only with --scope project, and project rules require the trusted project layer. Prefix rules cannot express an option anywhere, git -C or arbitrary wrappers. golaw.rules is a regular file, because a symbolic link is never loaded. A malformed rules file can discard all user and project rules for the session. codex execpolicy check proves that the file loads and the tested argv matches; it does not prove session dispatch or arbitrary shell interpretation.

A shell pre event is judged as a prospective write only for a sole apply_patch or applypatch here-document statement, optionally preceded by cd with one word and &&, and for a cat here-document with one visible output target; appended content is not a reconstructed whole file. Additional statements, pipes, ||, variables and substitutions receive the shell family's judgment and any available post detection. They do not justify a wider recognizer. An intercepted patch has only the Bash pre event. The workdir argument is absent from the hook payload. So the payload cwd may identify a different directory from the command's actual directory.

A failed multi-file patch can leave earlier files written without a post event. A running command can receive its post event later, or never. Codex has no PostToolUseFailure. Post findings are feedback about completed execution, never rollback.

Codex trust is read, never written: the installer prints the /hooks step when a definition it writes differs from the trusted record, and doctor asks Codex itself through codex app-server or compares the hash with the record. On Windows a process that Codex app-server starts may outlive doctor; on macOS and Linux doctor ends its whole process group. Ending a process tree on Windows needs a job object, and M4 adds no module for it.

## The Cursor guard

Cursor is a compatibility preview with no supported-enforcement claim in M4. Cursor stops a secret read by name at beforeReadFile, for exposure to the model only, and the shell denials at beforeShellExecution. A shell command is judged at preToolUse Shell as well, with the same English reason, any denial winning. Cursor cannot stop the disk read, and cannot stop writes until a live record proves the Write payload (A4, cut 13).

Cursor's beforeReadFile prevents exposure to the model, not the disk read. The event already carries the file content; the decoder drops that content and judges the name, so the boundary is model exposure.

Write and Delete capture records key names, never values or content. The key names of a Write or Delete payload are captured before the allow; nested key names are joined with dots and sorted. Capture success is not payload validation or write enforcement. Writes remain unenforced until a live record proves the Write payload, as A4 and cut 13 require; enforcement turns on with typed, versioned fixtures of that payload.

Post findings are advisory. Post feedback does not undo a write. The installed definition carries failClosed: true, which the documentation says blocks the action on a crash, a timeout, a non-zero exit or no output, so the allow JSON is always printed. That is the documented behavior of the host, not a tested live host, and doctor reports Cursor as a preview whose writes are not enforced.

## Local aids and the remote gate

Every local check is optional. Installing an agent guard opts into its denials; agent uninstall removes that integration. Local git checks are armed only by the developer and may be disabled without a finding.

M1 scans the worktree. M2 adds staged scanning and the optional git rungs. Both scans are local aids. Remote CI or the platform pipeline is the only hard gate. Full make ci runs there; mutation, fuzz, benchmarks and integration suites run on demand.

golaw setup opts a developer into the git rungs; init never arms them. Installed agent guards and developer-armed rungs are separate integrations. Each ladder switch can be false without a finding, before version checks or tool resolution. Changing these switches requires no re-enrollment and does not relax an installed agent guard. test_staged is off by default.

```yaml
ladder:
  pre_commit: false
  commit_msg: false
  pre_push: false
  test_staged: false
```

A false denial or a false finding is a defect. A rung or guard refuses only what it recognizes with certainty, and its reason must name the repair. Unsupported exotic constructs are stated limits, never a reason to widen a reader.

An adopting platform must demonstrate its remote stage before claiming that the kit is enforced there. Without that stage, the kit runs only where developers choose to run or install it.

## Optional git rungs

| Rung | M2 work |
|---|---|
| pre-commit | Staged scan and separate proposed-policy validation; `golangci-lint fmt --diff`, which names a whole-file difference and refuses nothing; affected-package lint limited with `--new-from-patch`, the formatters included; affected-package vet; staged gitleaks; optional affected-package `go test -race`; a file over the read bound named and left to the pipeline |
| commit-msg | Commit checks over the message file and staged changes |
| pre-push | Govulncheck over every non-deleted pushed tip using committed waivers |

The index git commits through is authoritative, including an alternate index in a linked worktree. Unstaged edits cannot hide a staged violation. The staged scan compares findings against the base and evaluates the proposed policy separately. A goast.goleak finding is compared by its package, read whole at the base, so a goroutine added beside one the base already starts without a goleak test is the inherited violation, and the first goroutine of a package is the commit's own. When a committed Go file of that package is over the read bound, the base cannot say whether it starts goroutines, so the finding is held back and the file named, and the rung leaves both to the pipeline. For package tools, the checkout is used when git reports its relevant Go inputs unchanged, a file a //go:embed pattern of an index package names included, and the checkout bytes of staged Go files match the index; otherwise a bounded copy of the index outside the repository supplies the bytes. The previously stated limit of files git status treats as clean still applies. A file git ignores is no Go input for that choice, even one a //go:embed pattern of an index package names, a stated limit and not a reason to widen the reading, because listing the ignored files would read them on every commit: the checkout is used in place and go embeds that file beside the staged ones. go vet accepts such a package, so the default ladder lets the commit go, while test_staged builds it and may refuse with the embed error go prints, as multiple files for type string, and a reason that names the off switch; delete or stage the ignored file, or switch test_staged off in golaw.yml. A rung test pins both answers. A change to go.mod or go.sum affects every package; other changes include their reverse importers.

The whole-file formatter diff is a notice; the lint step judges formatter issues on staged lines. A formatter that cannot execute or returns an unexpected status is a tool failure. Vet refuses diagnostics attributed to added lines and leaves inherited or unplaced diagnostics to the pipeline. During a merge in progress, the lint and staged gitleaks steps leave the combined staged diff to the pipeline because it includes changes the merge brought.

Copies are bounded at 512 MiB and 50,000 entries. A copy over those bounds or containing an unsupported path leaves the Go steps to the pipeline with the reason and the remedy; it is no finding of the commit. Go files ignored by git also leave those steps to the pipeline, since tools would read them in place and a copy would lack them. A staged file over the scanner's read bound is named and left to the pipeline, and so is a check the comparison with the base cannot measure, as when the base revision of a staged file does not parse: the commit cannot repair the base, so the rung names the check and its reason and lets the commit go, while scan --staged keeps exit 2 for it.

Pre-commit waits at most five seconds for its worktree's operating-system lock. A busy lock names the holder PID and asks for a retry after that process finishes. Normal completion and cancellation that returns through the cleanup path remove the isolated copy and release the lock. A killed process releases its operating-system lock but can leave a copy behind; before making another copy, the runner sweeps only owned trees whose creating process is certainly gone. An uncertain owner is retained, and a failed sweep is reported.

The pre-push rung runs govulncheck only. It scans every non-deleted pushed tip, using the policy's committed waivers, and refuses a reachable advisory without a valid waiver. An expired waiver does not cover that advisory. A scanner failure or unreachable database is reported as Unmeasured and does not block this rung. This exception belongs to pre-push; it does not turn a missing measurement into a clean scan. A scanner reporting a version different from its pin is refused, as is an exact kit.version mismatch in either direction for an enabled rung.

User commands lose GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE, GIT_COMMON_DIR and GIT_PREFIX; the kit's plumbing keeps them. A test that starts git therefore operates in its own working directory. The dedicated staged gitleaks invocation explicitly restores only the selected absolute GIT_INDEX_FILE, because gitleaks itself asks git for the staged diff.

The lefthook.yml asset hands golaw hook the commit-msg file and the pre-push remote and URL in single quotes, because lefthook 2.1.12 splices Git's arguments into sh -c unescaped; a space in them stays inside its argument. An argument that holds a single quote is a stated limit of the lefthook.yml asset: the absolute message path Git gives a commit in a linked worktree of a repository whose path holds an apostrophe, or a remote name or URL that holds one, leaves the quote open, so the hook fails with a shell syntax error before golaw runs and no ladder switch reaches it; commit from the main worktree, push through a remote whose name and URL hold no apostrophe, or run golaw setup --uninstall in that clone.

The pre-commit rung leaves migration, API-breaking and generation execution to the pipeline targets.

## Untrusted repositories

Agent hooks execute no repository code. They use trusted git plumbing, keep snapshots in memory, and never execute intercepted command text, make targets, generators, or repository tools. The git status and git hash-object of change detection run the clean filter driver the git configuration of the checkout names for a path, a long-running process filter included, and core.fsmonitor runs its hook, as any git command in that checkout does. The git merge-tree that compares a merge the command left in progress, and the git log --remerge-diff that compares a merge commit the command made, with the merge git makes by itself run the merge driver the git configuration of the checkout names for a path, as any merge in that checkout does, and keep the objects of that merge in a temporary object directory removed after, so none reaches the repository. A cloned repository names no such program, because git configuration is not cloned: a .gitattributes file names a driver only by its name, and the drivers are the person's own configuration and the tools they installed, such as git-lfs. A checkout copied with its .git directory keeps the configuration it was copied with, which the person's own git commands there run as well.

That Git-driver boundary also applies to the plumbing the rungs use. Developer-armed rungs additionally execute their declared tools and, when test_staged is enabled, repository tests. Arming a rung does not sandbox those programs or make an untrusted checkout safe to execute.

init writes only within the real repository root and refuses symlinked path components. It never arms git hooks. Templates contain no project-level agent files.

Policy authority is committed HEAD, or the enrolled bootstrap policy on an unborn branch. Until HEAD holds golaw.yml on a branch with commits, the agent hooks take the golaw.yml the index holds, or the checkout when nothing is staged, only when its bytes mean the policy the enrollment record holds, never through a link; any other state is a denial whose reason asks for golaw.yml to be committed, so a file an agent can edit never weakens the policy in force. The golaw.yml of the checkout is read up to 1 MiB, the bound init reads it with too: init refuses to enroll a longer one, and one grown past it after init is that denial until git holds it, staged or committed, a stated limit no policy of a person reaches. The indexed policy is a proposed replacement and cannot weaken the policy in force. Agent edits to golaw.yml are denied.

Missing or mismatched policy in an enrolled repository is an error. A positively unenrolled location receives a valid allow.

A path exception by hash covers only an installed agent artifact recorded by the installer. It never exempts source files.

## Secret boundary

The first layer denies recognized secret-material names in Read and shell inputs. A Read is judged both by the name it asks for and by the file its links lead to, so a link named like secret material and a link to it are both denied. The name it asks for keeps every element below the repository boundary, a directory link back to the root included. The second denies known credential-printing commands. Their exact patterns are executable data with red and near-miss fixtures.

The Read deny rules the installer writes for the @ reference gap cover only private key and keystore files, the Terraform variable files Terraform loads by itself (terraform.tfvars and *.auto.tfvars, and their JSON form), the service account files whose name ends in service-account.json or service_account.json, SSH keys, and cloud credential files. They live in the user settings, which the host applies to every project before any hook runs, so the broad name list stays with the hook, which judges each read in the repository that governs it. These rules cannot express an exception of their own: the host reads a bracket class without negation, and it joins every deny rule of the user settings in one matcher, so a negation rule for the templates would also lift the person's own deny rules for them. The two families that have templates are therefore named narrowly, so a template such as dev.example.tfvars, terraform.tfvars.example or service-account.example.json is readable, to Read and to @ references, as the hook allows it. The trade-off is that a variable file named for one environment, such as prod.tfvars, which Terraform reads only when -var-file names it, and a service account file named otherwise, such as service-account-prod.json, are no longer denied by these rules, so outside an enrolled repository nothing denies their Read (a read from an enrolled session is still judged by the session's repository, as the paragraph on placement says), and an @ reference to them, which no hook sees, reads them. Inside an enrolled repository too, an @ reference reads such a file, a variable file named for one environment or a service account file named otherwise, because the host reads it for the prompt that carries it before any hook runs; the hook still denies the agent's own Read of it and a shell command that names it, by its whole name list.

Inherited environment variables and secrets outside the recognized names remain exposed. Run the agent under an identity without long-lived credentials. Name checks do not prove that arbitrary file content is free of secrets.

## Recovery

Run golaw doctor before upgrading the kit or agent. Compare installed and validated versions, artifact hashes, resolved executable, policy pin, enrollment digests, and fail mode.

When a payload change, panic, or missing executable blocks work, a person selects the last validated kit tag from the compatibility history. Install that tag with go install or its signed release asset, then run golaw agent install --agent claude. For the selected integration, a person chooses the last validated kit and agent combination, installs that binary, restores the matching kit.version and enrollment digests through the same reviewed procedure, and reruns the corresponding agent install, --agent codex or --agent cursor. Codex additionally requires the /hooks review when its hook definition changed, plus project trust where a project installation is used. No recovery edits hooks.state and none bypasses a hook.

Restore the matching kit.version and enrollment digests as part of the person's reviewed change, committing the repository policy change and updating external enrollment through agent install, which enrolls the committed policy only as a tightening, never lowering a policy floor. The binary and pin must move together.

Run doctor again. From a checkout of the kit at the validated tag, since the harness ships with the kit and never with an adopting repository, replay the recovery-control row of go run ./tools/acceptance, which takes the binary away, puts the validated one back, runs agent install again and requires the allowed write through the installed invocation, before resuming work.

Retain the previous validated combination in the compatibility history after every upgrade. The first release has no previous golaw release; its acceptance demonstrates reinstalling the validated candidate. Marketplace distribution remains deferred until its pinned pointer requirement is met, and Cursor has no supported-enforcement claim in M4.

Any emergency relaxation belongs outside the repository in user scope. It must be time-boxed, owned, audited, and prominent in doctor. There is no repository-level advisory switch.
